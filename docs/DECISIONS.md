## Round 3 — 2026-10-21 (Asia/Taipei)

16. **TypeScript — YES (Felix's request; approach chosen by Claude, open to Felix's review).** The codebase is strict TypeScript, and the install promise stays: `git clone` (or ZIP) + one command, no `npm install`, no build step for users.
    - **How it runs:** Node runs the `.ts` files directly by stripping types. Runtime imports are only `node:` built-ins; types come in through `import type`, which is erased.
    - **Minimum Node: 24.12.0** (`engines` in package.json). Source: <https://nodejs.org/api/typescript.html> (history table). Type stripping is on by default since v23.6.0 / v22.18.0 and prints no warning since v24.3.0 / v22.18.0. It is marked **stable from v25.2.0 / v24.12.0**. We require the first stable LTS release. Checked on this Mac with Node v24.14.0: no warning.
      - By release line: on 22.x, stripping is on and warning-free from 22.18.0 but not marked stable; on 23.x it is on from 23.6.0 but warns; on 24.x it warns on 24.0–24.2, is warning-free from 24.3.0 and stable from 24.12.0; on 25.x it is stable from 25.2.0. On Node older than 22.18 / 23.6, `node bin/homebot.ts` fails with "Unknown file extension .ts". The README says how to fix that.
    - **Syntax limits, enforced by `tsconfig.json`.** Only erasable syntax is allowed: no enums, namespaces with code, parameter properties or import aliases. The settings `erasableSyntaxOnly` and `verbatimModuleSyntax` (`import type`) enforce this. Relative imports naming the `.ts` file is a **source convention**, not enforced: `allowImportingTsExtensions` only permits it, and the checker would also accept a `.js` path that Node then can't load. Such a mistake only shows up when Node loads the file (for product code, in the tests). The code is also checked with `strict`, `noUncheckedIndexedAccess` and `exactOptionalPropertyTypes`. Type assertions (`as`) appear only at JSON/plist boundaries, each with a comment. There is no `any` and no non-null `!`.
    - **Setup page script.** Browsers can't strip types. `src/setup-ui/app.ts` and `strings.ts` are compiled by `tsconfig.ui.json` (DOM lib) through `npm run build:ui`, and the generated `app.js` / `strings.js` are **committed**: users still install nothing. `npm run check:ui` and a test fail if the committed JS is stale.
    - **Dev-only dependencies:** `typescript` 7.0.2 and `@types/node` 24.x, pinned. They are only needed for `npm run typecheck`, `npm run build:ui` and the UI drift test (that test is skipped without them). Users never need them.
    - **Known limit:** Node refuses to strip types for files under `node_modules`. Installing Homebot as an npm package (`npm install -g`, `npx`) would therefore not work. The supported install is the repo folder (README); `package.json` `bin` points at `bin/homebot.ts` for that layout only.
    - **Rejected options:**
      - Committing compiled JS for all code: two copies of every file, plus drift risk on the main path.
      - Requiring a build/`npm install` step for users: this breaks the install promise.
      - `module.stripTypeScriptTypes` at runtime for the page script: it still prints an ExperimentalWarning on Node 24.14.
